Declare and propagate errors in Rust: `anyhow` and `thiserror`
==============================================================

There are two main crates to deal with errors in the Rust ecosystem:

* [`anyhow`](https://crates.io/crates/anyhow): flexible concrete Error type built on `std::error::Error`.
* [`thiserror`](https://crates.io/crates/thiserror): `derive(Error)` for struct and enum error types resources.

and both of them are very useful but suitable for **different contexts**.

Libraries: `thiserror`
----------------------

Libraries should prefer `thiserror` over `anyhow`. The reason is that errors from libraries are consumed by other
source code, and consumers can choose to interact with the error and recover (retry the operation, ignore the error,
try with a different value,...).

When returning errors from libraries all the information is relevant. `thiserror` provides a convenient way to
define error hierarchies and compose them in a way that the original error (the error type itself) is accessible to
the user to decide what to do.

The structure of the error and any relevant data is more important than the error message itself. With this principle
in mind, always use `assert_matches!` when testing the errors in unittests instead of asserting the error message.

Executables (and tests): `anyhow`
---------------------------------

Executables (and tests as a special type of executable) are consumed by humans. At this level, a good error message
together with [its context](https://docs.rs/anyhow/latest/anyhow/trait.Context.html) is much more relevant than
the error type or the nested chain of errors. This objective is much better satisfied by `anyhow` crate.
